1. Scope

Goal

VLMShift measures how the answers of one or more VLMs change when one or more conditions change.

Example: same image, same question, asked in English and then in Hindi. Does the model answer the same way? Does it make more mistakes?

  • Simple use: the native features (Core) are enough.
  • Advanced use: add modules (new models, new variations, new metrics, data packages such as Med). VLMShift is designed as a modular foundation that is easy to change.

What the tool does (in order of use)

  • Describe a dataset before evaluation
  • Organize the variants to compare: import the ones in the dataset or (bonus) create some with simple transformations, keeping the link to the original sample
  • Query the models, local (V1) or through an API (bonus)
  • Measure the shifts between conditions, with their uncertainty
  • Produce a traceable report

Planned in the design, not implemented in V1

  • Other task types (multiple choice, ordinal, numeric, localization)
  • Image classifiers without text
  • Interpretability: attention maps, and latent space probe for generative models (the probe for contrastive models is in V1).

What the tool does not do

  • Evaluate free-text answers (reports, descriptions)
  • Rank models in general, outside the effect of a variation
  • Train, fine-tune or correct a model
  • Monitor a model in production
  • Host or redistribute data

2. Glossary

Term Definition
Sample An image with its question, before any variation.
Sample ID The ID shared by all the variants of the same sample. It allows comparing them face to face (pairing).
Row ID The unique ID of each row (each variant), generated by the tool.
Axis What we vary in order to compare (language, site, image quality).
Level A value that an axis takes (EN, FR, HI for the language axis).
Reference level The level the others are compared to. Optional: without a reference, all pairs of levels are compared.
Controlled axis We modify the same sample, and only one thing changes.
Observed axis The categories already exist in the data (the sites, for example).
Variant A sample at a given level of the controlled axes. Keeps the ID of its sample.
Role What a column is used for (image, label, independent unit…). Declared in experiment.yaml.
Shift measure The shift in answers between the levels of an axis (compare), possibly recomputed within each level of other axes (split_by). Computed at step 5.
Primary comparison Bonus, optional. A comparison declared before running the models (e.g. EN against HI). If primary comparisons are declared, the correction applies only to them and the others are exploratory.
Task type The form of the question and of the answer. V1: yes/no only.
Run One complete execution of experiment.yaml on a set of models, identified by its fingerprint.
Analysis A computation of measures on a run, described by analysis.yaml. A run can have several analyses, without running the models again.
Answer reader What turns the raw answer of a generative model into yes or no: an answer list, a local small LLM, or both.
Probe A simple classifier that tries to guess a column (e.g. the site) from the internal representation of a model.
Package A set of data, rules and configurations built on Core (Med, for example).
Cell A combination of levels of the axes of a measure (e.g. language = HI, site = S1).
Independent unit A group of rows that are not independent of each other (e.g. the images of the same subject). The uncertainty is computed by randomly drawing these units.
Fingerprint A short code computed on a content (table, configuration). It changes as soon as a single value changes.
Status State of an answer: valid, INVALID (unreadable answer) or error (technical failure).
Variants table What is sent to the models: one row per variant, with the exact texts (prompt, or positive_prompt and negative_prompt).
Results table The variants table with the answers: one row per variant × model.

3. Data model

Principle

  • One big table. One row = one variant: what we show to the model (an image and a question).
  • The variants of the same sample share the same sample ID.
  • It can be split into several files, as long as the IDs allow gluing the pieces back together.
  • A few columns are required. All the others are free, and each can be used as an axis, alone or combined.
  • The configuration says what each useful column is for (its role). The others are ignored.

Column roles

Each role is played by one column of the table. The configuration says which column plays which role: column names are free.

Role Example column Required Default
Row ID id yes Generated by the tool at import
Sample ID sample_id no Computed by the tool (see below)
Image image (path) yes
Question question, or a template defined in the configuration if generative models
Contrastive sentences positive_text, negative_text if contrastive models Templates of the task.contrastive block
Label label: positive, negative or unknown yes
Axis language, site, quality at least one Type in experiment.yaml, reference in analysis.yaml
Independent unit subject no = sample ID
  • Label: unknown rows are excluded from the accuracy measures, but kept for the answer-change measures.
  • Independent unit: says which rows are not independent of each other (the images of the same subject). The uncertainty computation randomly draws these units, not the rows. Default: the sample ID.

Sample ID

It links the variants of the same sample, to compare them face to face: the same image, with the same question, in EN and in HI.

Situation Where the ID comes from
Variants created by the tool Set by the tool
Table in wide format (see below) One row = one sample
Imported table in long format Provided by the user, otherwise computed
  • Computation rule: same values in all the columns, except the row ID, the question, the contrastive sentences (positive_text, negative_text), the columns used by the templates (such as {concept}, translated in each language) and the controlled axes.
  • Several questions per image: when leaving out the template columns would put two rows of one sample at the same levels of the controlled axes (one question per concept, for example), these columns stay in the sample ID of those rows: they tell the questions apart. If two rows are still at the same levels, the table is refused (same_levels): their pairs would be random.
  • Must be provided if imported variants have different image files (an image blurred outside the tool, for example): the tool cannot guess which image it comes from.
  • Check: the audit (step 2) shows the number of samples and of variants per sample.

Long or wide format

The tool works in long format: one row per variant.

id sample_id language question
1 s17 EN Is there…?
2 s17 HI क्या…?

The wide format (one row per sample, one column per level) is accepted as input, then converted to long format at import.

sample_id question_EN question_HI
s17 Is there…? क्या…?

The long format stays readable when axes are crossed (7 languages × 3 image qualities = 21 columns in wide format).

Configuration (two YAML files)

File When Content Changing it…
experiment.yaml Before inference Data, roles, axes, question, answer reader, models Forces the models to run again
analysis.yaml After inference Analyzed run, references, measures, statistics, probe Can be run again as often as you like

Full schemas and checking rules: section 7.1.

Generation of altered images (bonus)

Not in V1: the generation block will be added to the experiment.yaml schema when it is developed. Optional. The tool creates new rows at step 1, which keep the sample ID of the original row. Only images can be generated.

Altered images

  • Available transformations: blank (blank), shuffle (shuffle, image of another sample), blur (blur), noise (noise), reduced resolution (resolution).
  • Each transformation creates a level of the declared axis (e.g. quality: blur). The original rows are at level original.
  • The transformed image is created only once per original image.
  • Each row that uses this image is duplicated with the transformed image (cartesian product). E.g. if s17 has an EN row and an HI row, the blur creates a blur-EN row and a blur-HI row. This way image quality can be crossed with the other axes.
  • Parameters and seed are recorded: same configuration → same images.

Translations

  • They are not generated by the tool: each language is an imported variant, present in the table (one row per language, with the same sample ID).

Reading answers (generative models)

Two possible readers, declared in the task block of experiment.yaml:

  • List (answers): the raw answer is lowercased, stripped of spaces and punctuation at the start and at the end, then compared to the yes and no lists. The lists are written in the YAML or in a separate file.
  • Local small LLM (reader_llm): it classifies the raw answer as yes, no or unclear. Temperature 0, name and version recorded, answers cached.
Declared Reading
answers only List only
reader_llm only Small LLM for all answers
Both List first; small LLM only if the list finds nothing
Neither Default list: yes = ["yes"], no = ["no"]
  • No match in the list, or unclear from the LLM → INVALID.

Small LLM safeguards

  1. Traceability: the decision_source column (list or llm) says where each decision comes from.
  2. Bias control: the report shows the share of decisions made by the LLM, per model and per level. An LLM that understands one language less well would otherwise create a false shift.
  3. Validation: the accuracy of the LLM is measured language by language on a set of hand-annotated answers (reader_llm.validation). Without this file, the report says "reader not validated".

Since the raw answers are stored, the reading can be redone with another reader without running the models again.

Contrastive models (task.contrastive block)

A contrastive model (CLIP and similar) does not answer with text: it compares the image to two sentences and says which one fits best.

  • Positive sentence: the concept is present (e.g. "a photo showing a circle").
  • Negative sentence: the concept is absent (e.g. "a photo with no circle").
  • The sentences come from the templates of the task.contrastive block, or from the positive_text and negative_text columns. To vary the language, use the columns, one row per language, as for questions.
  • The answers block does not apply to these models.

Columns added at step 3

Column Content Why
prompt The exact text sent to the generative models We know what the model really read. Nothing is rebuilt later.
positive_prompt, negative_prompt The two exact sentences sent to the contrastive models Same

Results table

Produced at step 4: one row per variant × model, with these columns. Physically, results.parquet contains only these outputs; it is linked to the variants by id (section 7.2).

Column Content
model Model name (models.name); versions in run_log.json
run Run ID
response Raw answer of the model
decision Answer as read (yes or no)
decision_source Generative models: list or llm (the reader that produced the decision)
reader_response Raw answer of the small LLM, if it was used
score_pos, score_neg Contrastive models: score of each sentence
margin Contrastive models: score_pos − score_neg
status valid, INVALID (unreadable answer) or error (technical failure)

Import of external results (bonus)

A results table produced elsewhere can be imported directly. The requirements are relaxed, because the tool does not run any model:

Role or column At import
Label, axis, decision, model Required
Sample ID, independent unit Optional (same defaults)
Image, question, response Optional (kept for traceability)
Row ID, run Generated at import
status Deduced: INVALID if decision is empty or is neither yes nor no

These results are marked "external, not verified" in the report.

Example

Table (the question column is omitted: it contains the question in the language of the row):

id sample_id image concept language quality label subject
1 s17 img_17.png circle EN original positive p42
2 s17 img_17.png circle HI original positive p42
3 s17 img_17_blur.png circle EN blur positive p42
4 s42 img_42.png circle EN original unknown p08
5 s42 img_42.png circle HI original unknown p08

Configuration:

# experiment.yaml
schema_version: 1
data: images.parquet
roles:
  sample_id: sample_id      # needed here because of row 3
  unit: subject
axes:
  language: {type: controlled}
  quality:  {type: controlled}
task:
  type: yes_no
  answers:
    yes: ["yes", "हाँ"]
    no:  ["no", "नहीं"]
models:
  - {name: qwen2.5-vl-7b, adapter: vlmevalkit}

# analysis.yaml
schema_version: 1
run: runs/<run>
axes:
  language: {reference: EN}
  quality:  {reference: original}

The image, question and label columns already carry the name of their role: nothing to declare in roles.

Reading:

  • Samples: s17 groups rows 1, 2 and 3; s42 groups rows 4 and 5.
  • Why provide sample_id: row 3 has a different image file. Without this column, the tool could not link it to s17. If the blur had been generated by the tool (generation block), it would not be needed.
  • Comparisons: 1 against 2 = effect of language; 1 against 3 = effect of blur.
  • Rows 4 and 5: label unknown, so only for answer change.
  • Uncertainty: computed by randomly drawing the subjects (p42, p08), not the rows.

File formats

  • Tables: Parquet (CSV accepted as input)
  • Configuration: YAML (experiment.yaml, analysis.yaml), read as YAML 1.2
  • Bonus — Converters to and from the VLMEvalKit TSV

4. Specification by step

Each step follows the same description: role, inputs, outputs, rules, edge cases, tests.

1. Data → 2. Audit → 3. Axes and task → 4. Inference → 5. Statistics → 6. Report

Step 1 — Data

Role: turn the user's dataset into a valid VLMShift table (and, as a bonus, create the requested altered images).

Inputs

  • A CSV or Parquet file
  • experiment.yaml (section 7.1)

Outputs

  • The VLMShift table (Parquet), with:
    • a generated row ID: a unique code created by the tool (e.g. l_3f9a1c0e7b2d4a58, computation in 7.4), which designates the row everywhere afterwards;
    • a sample ID, provided or computed (see section 3);
    • Bonus — the generated altered images, if requested.
  • The issues (issues.parquet): excluded rows and the reason
  • The table fingerprint: a short code computed from all its content. If a single value changes, the fingerprint changes. It proves that we are working on exactly the same data.

Rules

Import

  • Bonus — Convert wide format to long format, if needed.
  • Generate the row ID from its content, not from its position (computation in section 7.4).
    • Importing the same file again, even with the rows in another order, gives the same IDs.
    • Results already obtained therefore stay attached to the right rows.
  • Keep the original ID if there is one, after checking that it is non-empty and unique.
  • Check that each role marked required in section 3 has its column.
  • Rename the role columns to their standard name (e.g. outcome → label). These names are reserved: a free column cannot use them.
  • Check that each image exists and compute its fingerprint.
  • Accept only positive, negative or unknown in the label.
  • Compute the sample ID if it is not provided (rule in section 3).

Generation (bonus, if the generation block is present)

  • Altered images: one transformed image per original image and per transformation; each row that uses the original image is duplicated (rule in section 3). Parameters and seed recorded.
  • The number of rows produced (and therefore of model calls) is estimated and shown before generation.

Edge cases

Situation Behavior
Required role without a column Stop, clear message
Original ID empty or duplicated Warning. The generated row ID is still used
Image not found Row flagged and excluded
Empty label or other value Error. Never converted to negative
A sample contains two different independent units (e.g. two subjects) Error
A sample contains different labels Error
Two variants of a sample at the same level of all the axes Flagged
Strictly identical rows Flagged, only one kept
Axis with a single level Flagged: no comparison possible
Two different contents with the same ID (collision, 7.4) Error
Bonus — Shuffled image identical to the original Forbidden: always the image of another sample

Tests

  • A small dataset built on purpose, with one example of each edge case. We check that each one is flagged.
  • Two imports of the same file, rows shuffled, give the same IDs and the same fingerprint.
  • Bonus — The same dataset in wide format and in long format gives the same table.
  • Bonus — Same generation configuration run twice: same images, same rows.

Step 2 — Audit

Role: describe how the dataset is distributed, before running the models. Changes nothing.

Inputs

  • The VLMShift table
  • experiment.yaml (axes, roles)

Outputs

  • The counts per axis and per level (audit/counts.parquet, section 7.2)
  • Bonus — Figures

Rules

  • For each level of each axis: number of rows, samples and independent units; positive, negative, unknown labels; proportion of positives.
  • Bonus — Crosstabs: distribution of each axis against the other declared columns.
  • Samples: number, variants per sample, incomplete samples (missing levels).
  • Bonus — Minimum detectable shift for each planned comparison (method in section 5).

Edge cases

Situation Behavior
Empty cell or cell below the count threshold Flagged (threshold: 30 independent units)
Numeric column (age) Split into quartiles (configurable bounds as a bonus)

Tests

  • Synthetic dataset with a known distribution: the figures produced are exactly the expected ones.

Step 3 — Axes and task

Role: prepare exactly what will be sent to the models.

Inputs

  • The VLMShift table (with its variants)
  • experiment.yaml: task, axes

Outputs

  • The variants table, with the columns prompt, positive_prompt and negative_prompt (section 3), stored with its fingerprint

Rules

Final question

  • For each row, the tool writes the exact text sent to the model in the prompt column.
  • Example: the template "Is there a {concept} in this image? Answer yes or no." with concept = circle gives "Is there a circle in this image? Answer yes or no.".
  • This text is stored, not recomputed: we can always check what the model read, and all the models receive exactly the same text.
  • For contrastive models, same principle: the two sentences are written in positive_prompt and negative_prompt.

Axes

  • Each declared axis must match a column.
  • The axes declared here are the ones the shift measures can use (step 5).

Primary comparisons (bonus)

  • These are the comparisons that answer the question of the study, chosen before running the models (e.g. EN against HI).
  • Without them, the correction for multiple comparisons applies to all the comparisons of each measure (section 5.5).
  • With them, the correction applies only to these comparisons: it is lighter, so a smaller effect can be detected. The others are marked "exploratory".
  • They will be declared in experiment.yaml, so they are frozen before inference: declaring them in analysis.yaml would allow choosing them after seeing the results.

Edge cases

Situation Behavior
Template slot without a matching column Error
Contrastive model without positive and negative sentences Error
Empty value to fill the template Row excluded and flagged
Axis declared without a column Error

Tests

  • Same configuration run twice: same variants table (same fingerprint).
  • Templates filled correctly on known examples.

Step 4 — Inference

Role: get the answer of each model for each variant.

Inputs

  • The variants table
  • experiment.yaml: models, inference, task (answer reader)

Outputs

  • The results table (section 3)
  • The run log: versions, dates, parameters, fingerprints
  • The vectors of the models with embeddings: true (embeddings.parquet)
  • The validation of the small LLM (reader_validation.parquet), if reader_llm.validation is declared

Rules

  • Common interface for all models. Generative through VLMEvalKit, contrastive through our adapters.
  • Generative: raw answer stored, then read by the list and/or the small LLM (rules in section 3). No decision → INVALID. Source of the decision in decision_source.
  • Contrastive: one score for the positive sentence, one for the negative sentence. Decision = yes if the positive sentence wins, no otherwise. Tie → INVALID. Scores and margin stored.
  • Deterministic decoding by default (temperature 0).
  • Bonus — API: model version and call date recorded, answers cached.
  • Resume: a variant already processed is not run again.
  • Cache per model: one folder per model and settings, in workspace/cache/. Each output is keyed by the question: the image fingerprint and the exact texts sent. A question already asked is never asked again, whatever the run, the table, the labels or the axes (e.g. adding an 11th model, a model of another kind, or a corrected label). The cache keeps the raw outputs (answers, scores, vectors); the reading of the answers is redone if the reader changes.
  • If models.revision is not set, the cache cannot see a change of weights: set it for reference runs.
  • Bonus — External import: relaxed requirements (section 3), results marked "external".
  • Models with embeddings: true: they also provide the vector of each image (embed method), stored in embeddings.parquet and linked to the image (image_hash). An image used by several rows is computed only once.

Edge cases

Situation Behavior
Model with embeddings: true without an embed method Error
Small LLM not found or impossible to load Stop before inference
Technical failure: the adapter raises ModelError (7.3) New attempt (inference.retries), then status error (different from INVALID)
V2 — Model that does not read text (image classifier), on an axis that only changes the question "Not applicable"
Equivalent answer worded differently (synonym, other language) Read by the list; otherwise by the small LLM if declared

Tests

  • Answer readers (list and small LLM) tested on a set of hand-annotated answers, language by language. With reader_llm.validation, this test is redone on the actual infrastructure, before inference.
  • Fake model with known answers: the results table is the expected one.
  • Simulated interruption: the resume creates no duplicate and no gap.

Step 5 — Statistics

Role: compute each declared shift measure, with its uncertainty. Exact formulas in section 5.

Inputs

  • results.parquet, linked to variants.parquet by id (and embeddings.parquet for the probe)
  • analysis.yaml (section 7.1)

Outputs

  • The metrics table (metrics.parquet): one row per figure, with its counts
  • The probe results (probes.parquet)

Rules

Shift measures

  • A shift measure computes the shift in answers between the levels of an axis (compare, e.g. language: EN, FR, HI…).
  • With split_by, the same computation is redone within each level of other axes (e.g. split_by: [site]: the effect of language on each site). This is the site × language matrix.
  • If a reference is declared for the axis, each level is compared to it; otherwise, all pairs.
  • Several measures can be computed on the same inference: the models are queried only once (step 4).
  • Without a measures block: one compare measure per declared axis, without split.
  • A new analysis (analysis.yaml) can be run after inference, without running the models again, if it uses only columns that are already present (e.g. an observed axis such as the site).
  • A measure on a controlled axis is possible only if its variants were sent to the models.
  • Latent space probe: for each column of latent.targets and each model with vectors (section 5.7).

Data used by each computation

  • Pairing: for a controlled axis, only the samples present in all the compared levels are used. The excluded ones are counted.
  • Rows taken into account:
    • accuracy: positive and negative rows only;
    • answer change: all valid rows, unknown included;
    • INVALID: two computations (counted as an error, or excluded);
    • error: excluded, but counted in the coverage.
  • Counts: each figure carries the number of rows, samples, independent units, valid answers and INVALID.

Tests, intervals and corrections: see section 5.

Edge cases

Situation Behavior
Measure that uses an axis not declared in experiment.yaml Error
Reference or level absent from the data Error
latent block with no model that has vectors Error
Measure on a controlled axis whose variants were not sent to the models Error
Metric that cannot be computed (sensitivity with no positive) "Not estimable", never 0
Too few units for the bootstrap "Not estimable"
Model that always gives the same answer Flagged

Tests

  • Simulated data with a known effect: the effect is recovered, and the 95% interval contains the true value about 95 times out of 100.
  • Degenerate cases: a single row, only INVALID, a single class.

Step 6 — Report

Role: present the results in a readable, traceable and reproducible way.

Inputs

  • metrics.parquet, probes.parquet, audit/counts.parquet, reader_validation.parquet, issues.parquet, run_log.json, experiment.yaml and analysis.yaml

Outputs

  • The tables (CSV, Parquet), with their counts
  • Bonus — An HTML report and figures (SVG, PDF)
  • Bonus — A reproduction archive: configurations, fingerprints, versions

Rules

  • Each figure is shown with its counts and its corrected interval; the uncorrected 95% interval is shown next to it, marked "exploratory".
  • Sections: summary, audit, results per measure, latent space probe, reading of answers, coverage limits.
  • Reading of answers: share of decisions made by the small LLM, per model and per level, and accuracy of the LLM per language on the annotated set.
  • Bonus — If primary comparisons are declared, they are presented apart from the exploratory analyses.
  • Bonus — Imported results marked "external, not verified".
  • Usage notice: report.notice of analysis.yaml, shown at the top of the report.
  • Color never carries the meaning of a figure alone.

Edge cases

Situation Behavior
Value not estimable Shown as such
Incomplete run Report produced, partial coverage flagged

Tests

  • Each figure in the report is identical to the one in the metrics table.
  • Bonus — Regenerating the report from the archive gives the same report.

5. Statistical specification

5.0 Notation

All formulas are given for one model and one shift measure.

Symbol Meaning
A = (a₁, …, a_k) Axes of the measure
c A cell: a combination of levels of the axes (e.g. language = HI, site = S1)
L_c Rows of c with status valid
T_c Rows of c, excluding status error
yᵢ Label: 1 = positive, 0 = negative, ∅ = unknown
ŷᵢ Model decision: 1 = yes, 0 = no
P_c, N_c Rows of L_c with yᵢ = 1, with yᵢ = 0
e A sample (sample ID)
u An independent unit

Handling of INVALID: each metric is computed twice.

  • Valid: INVALID rows are excluded (L_c as defined).
  • Strict: for the accuracy metrics (Sens, Spec, BA), an INVALID counts as a wrong answer (ŷᵢ = 1 − yᵢ). For answer change, a pair that contains an INVALID counts as a change.
  • The yes rate is always computed on valid answers; the INVALID rate has only one version.

5.1 Base metrics (per cell)

They describe the behavior of the model in a single cell. They do not measure a shift: they are used to compute it in 5.2.

Sensitivity         Sens(c)  = Σ_{i∈P_c} ŷᵢ / |P_c|
Specificity         Spec(c)  = Σ_{i∈N_c} (1 − ŷᵢ) / |N_c|
Balanced accuracy   BA(c)    = (Sens(c) + Spec(c)) / 2
Yes rate            Yes(c)   = Σ_{i∈L_c} ŷᵢ / |L_c|
INVALID rate        Inv(c)   = |{i ∈ T_c : INVALID}| / |T_c|
Metric What it measures
Sens Among the present cases, the share the model detects. Low = it misses cases.
Spec Among the absent cases, the share the model recognizes as absent. Low = false alarms.
BA Overall performance, giving the same weight to present and absent cases. Does not depend on the proportion of present cases.
Yes Tendency of the model to answer "yes". Does not use the labels.
Inv Share of the answers that the model does not give in the requested form.

5.2 Shift metrics

A shift = a change in the behavior of the model between two levels a (reference) and b of an axis.

Shift metric Question Labels Axis type
Δ_BA (detail: Δ_Sens, Δ_Spec) Does the model do worse? yes all
Δ_Yes Does its tendency to answer "yes" change? no all
Δ_Inv Does it still answer as requested? no all
Answer change (detail: yes → no, no → yes) Does it change its mind on the same samples? no controlled
Bonus — Interaction I (5.3) Is the shift the same everywhere? depends on the metric combination of axes

Metric shift (Δ_BA, Δ_Yes, Δ_Inv)

For a metric M and two levels a (reference) and b of an axis, the other axes being fixed:

Δ_M(b, a) = M(b) − M(a)
  • Δ measures by how much M changes between a and b. Negative for BA = the model does worse at level b.
  • Δ_Sens and Δ_Spec are given as detail of Δ_BA, to see where the shift comes from (missed cases or false alarms).
  • With a reference: each level against the reference. Without a reference: all pairs.
  • Controlled axis: M(a) and M(b) are computed on the same samples E_ab (those that have a valid row at both levels).

Answer change (controlled axis only)

For e ∈ E_ab, let ŷₑᵃ and ŷₑᵇ be the decisions at the two levels.

Chg(a, b) = (n₁₀ + n₀₁) / |E_ab|
    n₁₀ = |{e : ŷₑᵃ = 1, ŷₑᵇ = 0}|        (yes → no)
    n₀₁ = |{e : ŷₑᵃ = 0, ŷₑᵇ = 1}|        (no → yes)
  • Chg measures the share of samples whose answer changes between a and b. 0 = identical answers, whether right or wrong.
  • The n₁₀ / n₀₁ detail gives the direction of the change.
  • Does not use the labels: unknown rows are included.

5.3 Combination of axes

Measure on two axes: the compare axis whose effect we measure (levels a, b) and a split_by axis used for splitting (levels g, h).

Effect per split level   Δ_M(b, a | g)
Interaction (bonus)      I_M(g, h) = Δ_M(b, a | g) − Δ_M(b, a | h)
  • Δ_M(b, a | g) measures the shift between a and b, computed only within level g of the split (e.g. the effect of language on site S1).
  • I_M measures whether this shift differs from one split level to another (e.g. does language penalize more on S1 than on S2?).
  • I_M = 0: the effect is the same in g and in h.
  • More than two axes: same principle, the effect is computed within each combination of the split axes.

5.4 Uncertainty (bootstrap)

For any statistic θ (a metric, a shift, an interaction):

  1. Randomly draw, with replacement, as many independent units as there are.
  2. Keep all the rows of the drawn units (a unit drawn twice counts twice).
  3. Recompute θ → θ*.
  4. Repeat R times.
  5. 95% interval: 2.5% and 97.5% percentiles of the θ*.
  • R = stats.bootstrap (2000 by default), seed stats.seed, recorded.
  • A sample belongs to a single unit (checked at step 1): pairs stay together.

5.5 Significance and multiple comparisons

Rule

  • A shift is significant if its interval (5.4) does not contain 0.
  • With m comparisons, each interval is computed at level 1 − α/m instead of 1 − α (Bonferroni correction). α = stats.alpha (0.05 by default).
  • The uncorrected 95% intervals are also computed and shown as exploratory: they are not used to decide significance.
  • Value of m:
    • by default, the number of comparisons of a measure for a model, all split_by cells included (e.g. 7 languages, reference EN → 6 comparisons; split over 11 sites → m = 66 → 99.92% intervals);
    • if primary comparisons are declared: their number (e.g. 3 → 98.3% intervals). The other comparisons stay at 95% and are marked "exploratory".

Option: classical tests (controlled axis, yes/no answers)

Reported for information. They are not used to decide significance.

2 levels — exact McNemar:
    p = min(1, 2 · P(X ≤ min(n₁₀, n₀₁)))     with X ~ Binomial(n₁₀ + n₀₁, 1/2)

k levels — Cochran's Q:
    Q = (k − 1) · (k · Σⱼ Cⱼ² − N²) / (k · N − Σₑ Rₑ²)     ~ χ²(k − 1)
    Cⱼ = number of "yes" at level j
    Rₑ = number of "yes" of sample e
    N  = Σⱼ Cⱼ
  • McNemar tests whether the yes → no and no → yes changes are unbalanced. Cochran does the same for more than two levels.
  • Computed only if each independent unit contains a single sample.

5.6 Non-estimable cases and minimum detectable shift

Not estimable (shown as such, never 0) if:

  • the denominator of the metric is zero (e.g. |P_c| = 0 for Sens);
  • fewer than n_min independent units in a cell (default n_min = 30, adjustable with stats.min_units in analysis.yaml).

Minimum detectable shift (bonus, audit of step 2), with z = z₁₋α/₂ + z₁₋β ≈ 2.80 (α = 0.05, power 80%), and n the number of independent units:

Observed axis     MDE ≈ z · √( p(1 − p) · (1/n_a + 1/n_b) )
                  p = expected proportion (default: the one observed on the whole table)

Controlled axis   MDE ≈ z · √( d / n )
                  d = expected proportion of answer changes (default 10%)

5.7 Latent space probe

Question: is a column (e.g. the site) readable in the internal representation of a model? If so, the model has encoded this information and may use it instead of the image content.

V1 scope: contrastive models with embeddings: true, image vector. VLMEvalKit does not give access to the vectors of generative models.

Computation, for each model and each target column of latent.targets:

  1. Inputs: the vector vᵢ of each image and the value of the target column. For the label, only positive and negative rows are kept.
  2. An image appears only once, even if it is used by several rows.
  3. Simple classifier (logistic regression) that predicts the target value from vᵢ.
  4. K-fold cross-validation (latent.folds, 5 by default), split by independent unit: the same unit is never in both training and test (no leakage).
  5. Result: the balanced accuracy of the probe on the test folds. Interval: bootstrap by independent unit on these test predictions, without retraining the probe (5.4).

Noise floor: the same probe, trained on target values randomly shuffled (average of 5 shuffles, seed stats.seed). Only a score clearly above this floor counts.

Probe(target, model) = BA of the probe − BA of the probe on shuffled values
  • Chance: 1 / number of different values of the target.
  • A successful probe shows that the information is present, not that the model uses it.
  • Uses: compare models (which one encodes the site the least?); compare two targets for one model (does it encode the site more than the label?).
  • Probing a column that changes the text (the language) makes no sense: the probe works on the image vector.

Model (inference/base.py)

class Model:
    def __init__(self, name: str, id: str, revision: str | None, params: dict): ...

    # Description
    kind: Literal["generative", "contrastive"]
    supports_embed: bool = False
    batch_size: int = 8                      # can be overridden by models.params.batch_size
    def info(self) -> dict: ...              # versions, revision: written in run_log.json

    # Lifecycle
    def load(self) -> None: ...
    def unload(self) -> None: ...

    # Generative only
    def generate(self, images: list[str], prompts: list[str], params: dict) -> list[str]: ...
    # Contrastive only: one pair (positive score, negative score) per image
    def score(self, images: list[str], positives: list[str], negatives: list[str]) -> list[tuple[float, float]]: ...
    # Optional
    def embed(self, images: list[str]) -> list[list[float]]: ...

    def is_correct(self, decision: str, label: str) -> bool | None: ...   # None if label = unknown

7.4 Computation of fingerprints and IDs

  • ID: the name of a row. It links the files to each other (an answer in results → its row in variants).
  • Fingerprint: the signature of a whole content (table, configuration). Same content → same fingerprint. It is used to resume a run without redoing the work, to guarantee that two models saw exactly the same data, and to trace each figure.

Everything is computed with SHA-256, then truncated to 16 hexadecimal characters. A collision detected at import → error.

What Computed from Format
image_hash The bytes of the image file 64 characters (full code)
id (row) The content of the row: all its columns except id l_ + 16 characters
sample_id (if computed) The columns of the rule in section 3 s_ + 16 characters
Table The sorted list of the ids 16 characters
Variants The table fingerprint + the templates used by the kinds of model present 16 characters
Run experiment.yaml + the variants fingerprint 16 characters
Model (cache) Its settings: adapter, id (or name when there is no id), revision, params, inference, except retries 16 characters
Question (cache entry) The image fingerprint + the texts its kind of model receives (prompt, or the two sentences) 16 characters
Analysis analysis.yaml, the run designated by its fingerprint 16 characters

Canonical form (so that all modules compute the same code)

  • Configuration: read, checked, default values filled in, then written as sorted JSON, without spaces, in UTF-8. The paths (data, workspace, run) are excluded. Comments, key order and default values written explicitly therefore change nothing.
  • Row: columns sorted by name, values converted to text, text normalized in Unicode NFC, null kept.

Consequences

  • Running the same experiment.yaml again finds the same run: the resume is automatic.
  • Adding or removing a model creates a new run, but the unchanged models are taken from the cache, without recomputation, even when the new model is of another kind.
  • Any change to the data (even a corrected label) creates a new table, therefore new IDs and a new run. A result thus stays attached to the exact data that produced it.
  • The same file, rows in another order, keeps its IDs and its fingerprint.

7.5 Shared test dataset

First thing to do. If it does not exist yet in the code, this test set must be created before any other development. One person prepares it; everyone uses it afterwards.

What it is for: everyone tests their module without waiting for the others'. E.g. whoever codes the statistics starts from results that are already written and checks that they find the expected figures, even if inference does not exist yet.

Element Content
